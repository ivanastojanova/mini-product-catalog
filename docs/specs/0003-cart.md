# Spec 0003: Persistent Cart (guest + logged-in, server-side)

**Status:** Done — all build-order steps landed and the browser click-through passed.

**Phase:** 3 — see [docs/PLAN.md](../PLAN.md) for live status/checklist.

**Related:** [ADR 0004](../adr/0004-standalone-commerce-api-service.md) (cart lives in `apps/api`), [ADR 0005](../adr/0005-cookie-presence-route-protection.md) (every protected apps/api endpoint verifies the session itself), [Spec 0002](0002-auth.md) (sessions, cookies). Decision record: [ADR 0006](../adr/0006-cookie-guest-cart-merged-on-login.md).

## Context

Today's cart is a placeholder: `apps/web/app/api/cart/route.ts` keeps a per-process in-memory `Map<slug, quantity>` shared by *every* visitor, resets on restart, and randomly fails ~40% of the time to demo optimistic rollback. `features/products/api/cart.ts` and `useAddToCart` call it same-origin.

Phase 3 replaces it with a real cart owned by `apps/api` (commerce domain), usable by guests and logged-in customers, surviving restarts and devices (for logged-in users). Phase 4 (checkout) will consume this cart, so the shape should not need reworking then.

## Decision 1 — Guest cart identity: cookie-backed cart token

- `apps/api` sets an httpOnly `cart_token` cookie (same options as the session cookie: `SameSite=Lax`, `Secure` in prod, `path=/`, 30-day `maxAge`, refreshed on each write) holding a random 32-byte base64url token.
- The DB stores only the **SHA-256 hash** (`carts.guest_token_hash`), reusing `generateSessionToken`/`hashSessionToken`. Cart contents are low-sensitivity, but the token is a bearer credential and the helpers already exist and are tested, so the cost is near zero.
- The cart row is created **lazily on the first add**, not on `GET /cart`. A bare visit or a bot hitting `GET /cart` creates nothing; the response is just `{ items: [] }`.
- Cart ID is never a guessable integer in the cookie.

**Per-request resolution** (one helper, `resolveCart({ sessionToken, cartToken })` in `apps/api/src/cart/lib/resolveCart.ts` — takes the raw cookie values rather than the Fastify request, so it's testable without a server; route handlers read the cookies. Pure lookup, never creates rows):
1. Valid session → the customer's cart (get-or-create). A `cart_token` cookie, if present, is ignored here (it is only consumed by the login merge, below).
2. Else `cart_token` cookie matching an unexpired guest cart → that cart.
3. Else → no cart (reads return empty; the first add creates one and sets the cookie).

## Decision 2 — Merge on login/register

Done **server-side inside the login and register handlers**, in a single DB transaction, after credentials are verified and before the response is sent.

- **Login:** read `cart_token` → find guest cart → merge into the customer's cart (get-or-create) → delete the guest cart → clear the `cart_token` cookie.
- **Register:** new customer has no cart, so the guest cart is simply *adopted* (`customer_id` set, `guest_token_hash` nulled). No item merging.
- **Failed login never touches the guest cart.**
- **Merge policy (proposed):** per slug, **sum quantities, capped at the per-line max**. Slugs only on one side are carried over as-is.
- No cart cookie, unknown token, or expired guest cart → no-op, login proceeds normally. A dead `cart_token` cookie is still cleared.
- **A merge failure never blocks sign-in.** `mergeCartOnAuth` (`apps/api/src/cart/lib/mergeOnAuth.ts`, shared by both handlers) catches the error and logs it. The transaction has rolled back, so both carts are intact, and the `cart_token` cookie is left in place so the next login retries. The tradeoff: the shopper signs in with a cart that is missing their guest items until that retry, instead of seeing a login error for a problem they can't fix.
- Concurrent logins (two tabs): the second finds the guest cart already gone → no-op. The transaction makes it all-or-nothing. (`better-sqlite3` transactions are synchronous, so within one process they can't interleave; a multi-process or Postgres deploy would need to revisit this.)
- **Logout** leaves the customer's cart on the server and does not create a guest cart; the browser is left with an empty cart.

*Why not an explicit `POST /cart/merge` called by the client after login:* two round trips with a window where the client is logged in but unmerged, and it can be skipped or fail halfway. Doing it in the handler makes it impossible to log in without the merge being attempted.

## Decision 3 — Replacing the placeholder

**Data model** (apps/api, Drizzle, new migration):

`carts`
| column | type | notes |
|---|---|---|
| `id` | integer PK autoincrement | |
| `customer_id` | integer, nullable, **unique**, FK → customers, `ON DELETE CASCADE` | one cart per customer; SQLite allows many NULLs under UNIQUE |
| `guest_token_hash` | text, nullable, **unique** | |
| `created_at` / `updated_at` | integer (unix ts) | `updated_at` drives guest expiry |
| | | `CHECK` exactly one of `customer_id` / `guest_token_hash` is non-null |

`cart_items`
| column | type | notes |
|---|---|---|
| `cart_id` | integer, FK → carts, `ON DELETE CASCADE` | |
| `product_slug` | text | |
| `quantity` | integer, `CHECK` 1..MAX_LINE_QUANTITY | |
| `added_at` | integer (unix ts) | |
| | | PK `(cart_id, product_slug)` |

- **No prices in the cart.** The cart stores `slug + quantity` only. Price is looked up at read/checkout time; the *snapshot* happens when Phase 4 creates an order. A stored price would go stale and be a second source of truth next to the CMS.
- **Slug, not CMS id**, since slug is what apps/web already uses everywhere. Tradeoff: a slug renamed in the CMS orphans cart lines.
- `MAX_LINE_QUANTITY = 10` (proposed), enforced in the API and by `CHECK`.

**Endpoints** (all in apps/api, all `credentials: "include"` from the browser):

| route | behavior |
|---|---|
| `GET /cart` | `{ items: [{ slug, quantity }] }`; empty if no cart. |
| `POST /cart/items` `{ slug, quantity? = 1 }` | **Increment** (matches the "Add to cart" button). Creates cart + sets cookie if needed. Returns the line's new state. |
| `PUT /cart/items/:slug` `{ quantity }` | **Set absolute** quantity — idempotent, safe to retry (for a future cart page). |
| `DELETE /cart/items/:slug` | Remove a line. Idempotent. |

Validation: `slug` non-empty string, `quantity` integer within bounds, else `400`. Slug existence is checked against apps/cms.

**Bodiless requests must not send `Content-Type: application/json`.** Fastify answers `400` to a JSON content-type with an empty body, so apps/web's cart fetch wrappers set that header only on `POST`/`PUT` (pinned by a test in `cart.test.ts`). `PUT` sets an existing line only (`404` if absent; `0` is invalid, use `DELETE`) and never calls the CMS; `DELETE` is always `204` and keeps the empty cart so the guest cookie stays valid.

**CORS must change:** `@fastify/cors` defaults to `methods: 'GET,HEAD,POST'` (verified in v11.3.1), so `PUT`/`DELETE` from the browser fail preflight. The options now live in `apps/api/src/corsConfig.ts` with an explicit `methods` list, shared by `server.ts` and the preflight test. JSON bodies and non-simple methods force preflight, and the specific-origin CORS policy from ADR 0004 covers cross-site CSRF; `SameSite=Lax` covers the rest.

**apps/web changes:**
- Delete `app/api/cart/route.ts` (including the artificial delay + random 503).
- New `features/cart/` module (per AGENTS.md; carts don't belong in `features/products`): `api/` (fetch wrappers), `queries/cartKeys.ts`, `hooks/`, `lib/cartMath.ts` (pure optimistic-update helpers), `types/`. Deleted: `features/products/{api,types}/cart.ts`, `features/products/hooks/useAddToCart.ts`, `productKeys.cart`, and `app/api/cart/route.ts`.
- New `shared/api/client.ts` (`apiFetch` + `extractErrorMessage`) — the apps/api counterpart to `shared/cms/client.ts`, hoisted out of `features/auth/api/auth.ts` (which now imports it) so cart and auth share one place that knows about `NEXT_PUBLIC_API_URL` and `credentials: "include"`.
- The optimistic add lives in `features/cart/hooks/addToCartMutation.ts` as a plain options factory, so rollback is tested against a real `QueryClient` without a React renderer (no new dependency; Vitest stays `environment: "node"`).
- **Query shape changes** from one query *per slug* (`GET /api/cart?slug=`) to one whole-cart query (`cartKeys.current()`); `AddToCartButton` derives its quantity from it via `select`. Fewer requests, and a future mini-cart reads the same cache. The optimistic add + rollback logic in `useAddToCart` carries over, operating on the cart list.
- `useLogin`/`useRegister` success handlers **invalidate the cart query** (login changes the cart's contents server-side). `useLogout` instead sets the cached cart to empty — logout leaves the customer's cart on the server and gives the browser no cart, so there's nothing to refetch.
- The cart is client-fetched only. apps/web's server can't see the apps/api cookie in a way worth relying on, and a cart page doesn't need SSR.
- **Lost on purpose:** the 40% random failure that made rollback easy to demo. Rollback is covered by a hook test instead (see Testing).

## Settled decisions

1. **Merge policy: sum + cap.** Per slug, quantities are added and capped at `MAX_LINE_QUANTITY`. Rejected: customer's cart wins (items appear to vanish), guest wins (clobbers a saved cart).
2. **Slug validation: yes, against apps/cms on add.** apps/api makes a server-side HTTP call to the CMS and returns `404` for unknown slugs. apps/api gains a runtime dependency on apps/cms for adds and a `CMS_API_URL` env var. The merge does not re-validate (the lines were already validated when added).
3. **Guest token: store the SHA-256 hash**, reusing `generateSessionToken`/`hashSessionToken`.
4. **Stock: not enforced in the cart.** Only the per-line cap applies. Stock checks and reservation belong to Phase 4.

## Out of scope

- Checkout, order creation, price snapshots, stock reservation (Phase 4).
- Cart page / mini-cart UI beyond keeping the product-page button working (Phase 6). No cart page was added; the merge was click-tested through the "N in cart" label on product pages.
- Expired guest-cart cleanup job: guest carts past 30 days of inactivity are treated as nonexistent on lookup; physical deletion stays lazy/TBD, same as expired sessions.
- Saved-for-later, coupons, multi-currency carts.

## Testing requirements (cart merge is money-adjacent; tests ship with the code)

All in `apps/api`, via Fastify `.inject()` against an in-memory migrated DB, matching the auth tests.

- `resolveCart`: session beats guest cookie; guest cookie alone; neither; expired guest cart treated as absent; unknown token.
- Add/set/remove: increment, cap at max, `quantity` bounds, invalid slug body, idempotent `PUT`/`DELETE`, lazy cart creation + cookie set only on first add, `GET` on a fresh visitor creates no row.
- **Merge** (`mergeGuestCart`): disjoint slugs, overlapping slugs summed, sum capped, empty guest cart, no cart for customer yet, guest cart row deleted afterward, cookie cleared, **failed login leaves guest cart intact**, replaying a merge is a no-op.
- Register adopts the guest cart.
- Isolation: customer A cannot read or mutate customer B's cart or a guest cart they don't hold the token for.
- apps/web: `useAddToCart` optimistic update + rollback on error (mocked fetch), replacing the lost random-failure demo.
- Manual browser click-through: add as guest → log in → items merged → reload/another browser still shows them → log out → empty.
