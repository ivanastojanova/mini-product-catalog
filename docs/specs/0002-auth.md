# Spec 0002: Customers & Auth (session cookies)

**Status:** In progress

**Phase:** 2 — see [docs/PLAN.md](../PLAN.md) for live status/checklist.

**Related ADR:** [0003-session-cookie-auth.md](../adr/0003-session-cookie-auth.md) (to write — captures the session-cookie-vs-JWT decision in isolation).

## Context

apps/web needs real customer accounts (register, login, logout) ahead of Phase 3 (cart) and Phase 4 (checkout), both of which need to know *who* is shopping. apps/cms's `Users` collection is unrelated — it only gates the Payload admin dashboard and must stay that way (content vs. commerce domain split, see [ADR 0001](../adr/0001-monorepo-content-commerce-split.md)).

## Decision summary

Hand-rolled session-cookie auth, own tables, own code — no NextAuth, no Payload auth, no JWT.

**Why not JWT:** JWT's actual advantage is verifying identity *without calling back to the issuer* — useful when multiple independent services each need to check who someone is. In this app, only apps/web ever checks customer identity (apps/cms never sees a customer token). That scenario doesn't exist here, so JWT buys nothing but extra complexity (signing, refresh rotation, "where do I store the refresh token" as its own sub-problem) in exchange for a property (statelessness) we don't need. A session cookie + DB table is simpler, trivially revocable (delete the row — no blocklist needed), and equally "decoupled from Payload."

**Why not NextAuth / Payload auth:** both pull in a provider model and conventions aimed at generic use cases; this app's auth surface is small enough (register/login/logout, no OAuth/social login planned) that hand-rolling is more legible for learning purposes and avoids a dependency whose internals you can't fully see.

## Data model

Two tables in apps/web's own SQLite DB (`apps/web/web.db`, separate file from apps/cms's `payload.db`), managed by Drizzle (`apps/web/shared/db/schema.ts`):

### `customers`

| column | type | notes |
|---|---|---|
| `id` | integer, PK, autoincrement | |
| `email` | text, unique | login identifier; uniqueness enforced at DB level too |
| `password_hash` | text | bcrypt, cost factor 12 — **never** the plaintext |
| `name` | text | display only |
| `created_at` | integer (unix timestamp) | defaults to `unixepoch()` at insert time |

### `sessions`

| column | type | notes |
|---|---|---|
| `id` | text, PK | **SHA-256 hash** of the random cookie value — not the raw value. A DB leak alone can't be replayed as a valid session; you'd need the original unhashed cookie too. |
| `customer_id` | integer, FK → customers.id, `ON DELETE CASCADE` | deleting a customer auto-deletes their sessions |
| `expires_at` | integer (unix timestamp) | hard deadline even without explicit logout |
| `created_at` | integer (unix timestamp) | defaults to `unixepoch()` |
| `user_agent` | text, nullable | captured at login; for a future "active sessions" UI |
| `ip_address` | text, nullable | same |

## Request flows

### Register (`POST /api/auth/register` — exact path TBD when built)

1. Validate email format + password minimum length (TBD: length policy).
2. Check email not already taken (DB unique constraint is the backstop; app-level check gives a nicer error message).
3. `hashPassword(plaintext)` → bcrypt hash.
4. Insert `customers` row.
5. Generate session token (random bytes for the cookie, SHA-256 hash of it for the `sessions.id` column).
6. Insert `sessions` row with `expires_at` = now + TBD duration (suggest 30 days, sliding or fixed TBD).
7. Set httpOnly, Secure (in prod), SameSite=Lax cookie containing the **raw** token (never the hash).
8. Return customer info (not the password hash) to the client.

### Login (`POST /api/auth/login`)

1. Look up customer by email.
2. `verifyPassword(plaintext, storedHash)`.
3. On success: same session-creation steps as register (4–7 above, skipping customer insert).
4. On failure: generic "invalid email or password" — never reveal which one was wrong (avoids leaking which emails are registered).

### Logout (`POST /api/auth/logout`)

1. Read session cookie, hash it, delete the matching `sessions` row.
2. Clear the cookie.

### Session check (used by middleware / `useSession`)

1. Read cookie → hash → look up `sessions` row → check `expires_at` not passed → join to `customers` for display info.
2. No row or expired → treat as logged out (and arguably delete the expired row — TBD: lazy cleanup vs. a cron/cleanup job).

## Open questions / TBD (resolve while implementing, update this doc after)

- ~~Exact API route paths~~ — resolved: `/api/auth/*` Next.js route handlers (`POST /api/auth/register` built; `login`/`logout` to follow the same pattern), not server actions — matches the existing `/api/cart`, `/api/revalidate` convention in this repo.
- ~~Password minimum requirements~~ — resolved: length only, 8 characters minimum. No complexity rules (matches NIST 800-63B guidance that length is the stronger signal; complexity rules mostly push users toward predictable substitutions).
- ~~Session duration + sliding vs. fixed~~ — resolved: 30 days, fixed. Simpler to reason about than sliding expiry; revisit if "stay logged in indefinitely while active" becomes a real user complaint.
- Expired-session cleanup strategy — still TBD (lazy cleanup on next lookup vs. a periodic job). Not needed until the session-check code path (login/`useSession`) is built.
- Rate limiting on login attempts (brute-force protection) — still TBD, likely out of scope for this learning project; flagged as a known gap if skipped.
- `sessions.ip_address` is not currently populated — local dev has no reverse proxy setting `x-forwarded-for`, and storing something misleading (e.g. always `::1`) seemed worse than leaving it `null`. Revisit once there's a real deploy target with a known proxy header to trust.
- Auto-login on register — resolved: yes, register creates a session and sets the cookie immediately (steps 4–7 in the register flow above), matching the flow as originally documented.

## Out of scope for this phase

- Password reset / forgot-password flow.
- Email verification.
- OAuth / social login.
- "Active sessions" management UI (schema supports it later; no UI planned now).
