# Spec 0002: Customers & Auth (session cookies)

**Status:** In progress

**Phase:** 2 — see [docs/PLAN.md](../PLAN.md) for live status/checklist.

**Related ADRs:** [0003-session-cookie-auth.md](../adr/0003-session-cookie-auth.md) (session-cookie-vs-JWT decision), [0004-standalone-commerce-api-service.md](../adr/0004-standalone-commerce-api-service.md) (mid-phase restructure: this domain moved from Next.js API routes inside apps/web into a standalone `apps/api` service — **all paths below reflect that move**, not the original apps/web-hosted routes).

## Context

The storefront needs real customer accounts (register, login, logout) ahead of Phase 3 (cart) and Phase 4 (checkout), both of which need to know *who* is shopping. apps/cms's `Users` collection is unrelated — it only gates the Payload admin dashboard and must stay that way (content vs. commerce domain split, see [ADR 0001](../adr/0001-monorepo-content-commerce-split.md)).

This domain was originally built as Next.js API routes living inside `apps/web` (a backend-for-frontend shape). Partway through the phase, that was deliberately restructured into a third standalone app, **`apps/api`** (Fastify, port 4000) — see ADR 0004 for the full reasoning and the CORS/cross-origin-cookie consequences.

## Decision summary

Hand-rolled session-cookie auth, own tables, own code, own service — no NextAuth, no Payload auth, no JWT.

**Why not JWT:** JWT's actual advantage is verifying identity *without calling back to the issuer* — useful when multiple independent services each need to check who someone is. In this app, only apps/api ever checks customer identity. That scenario doesn't exist here, so JWT buys nothing but extra complexity (signing, refresh rotation, "where do I store the refresh token" as its own sub-problem) in exchange for a property (statelessness) we don't need. A session cookie + DB table is simpler, trivially revocable (delete the row — no blocklist needed).

**Why not NextAuth / Payload auth:** both pull in a provider model and conventions aimed at generic use cases; this app's auth surface is small enough (register/login/logout, no OAuth/social login planned) that hand-rolling is more legible for learning purposes and avoids a dependency whose internals you can't fully see. (NextAuth is also Next.js-specific, which stopped being relevant once auth moved to a plain Node/Fastify service.)

**Why a separate `apps/api` service (not Next.js route handlers in apps/web):** see ADR 0004. Short version: the project's goal is a frontend that treats its backend as a genuinely separate service, the same way apps/web already treats apps/cms. This means every auth request from the browser is cross-origin (different port), handled via CORS (`@fastify/cors`, specific origin + `credentials: true`) and `credentials: "include"` on every client-side fetch — the cookie mechanics from ADR 0003 are otherwise unchanged.

## Data model

Two tables in apps/api's own SQLite DB (`apps/api/commerce.db`, separate file from apps/cms's `payload.db`), managed by Drizzle (`apps/api/src/db/schema.ts`):

### `customers`

| column | type | notes |
|---|---|---|
| `id` | integer, PK, autoincrement | |
| `email` | text, unique | login identifier; uniqueness enforced at DB level too |
| `password_hash` | text | bcrypt, cost factor 12 — **never** the plaintext |
| `name` | text | display only |
| `created_at` | integer (unix timestamp) | defaults to `unixepoch()` at insert time |

### `sessions`

| column | type | notes |
|---|---|---|
| `id` | text, PK | **SHA-256 hash** of the random cookie value — not the raw value. A DB leak alone can't be replayed as a valid session; you'd need the original unhashed cookie too. |
| `customer_id` | integer, FK → customers.id, `ON DELETE CASCADE` | deleting a customer auto-deletes their sessions |
| `expires_at` | integer (unix timestamp) | hard deadline even without explicit logout |
| `created_at` | integer (unix timestamp) | defaults to `unixepoch()` |
| `user_agent` | text, nullable | captured at login; for a future "active sessions" UI |
| `ip_address` | text, nullable | same |

## Request flows

All routes below are served by **apps/api** (Fastify), not apps/web. apps/web's `features/auth/api/auth.ts` calls them cross-origin via `NEXT_PUBLIC_API_URL`, with `credentials: "include"` on every request.

### Register (`POST /auth/register`)

1. Validate email format + password minimum length (8 chars, length only).
2. Check email not already taken (case-insensitive; DB unique constraint is the backstop, app-level check gives a nicer error message — `409`).
3. `hashPassword(plaintext)` → bcrypt hash.
4. Insert `customers` row.
5. Generate session token (random bytes for the cookie, SHA-256 hash of it for the `sessions.id` column).
6. Insert `sessions` row with `expires_at` = now + 30 days (fixed, not sliding).
7. Set httpOnly, Secure (in prod), SameSite=Lax cookie containing the **raw** token (never the hash), via `reply.setCookie` (`@fastify/cookie`).
8. Return customer info (not the password hash) to the client, `201`.

### Login (`POST /auth/login`)

1. Look up customer by (lowercased) email.
2. `verifyPassword(plaintext, storedHash)`.
3. On success: same session-creation steps as register (4–7 above, skipping customer insert), `200`.
4. On failure: generic `401 "Invalid email or password"` — never reveal which part was wrong (avoids leaking which emails are registered).

### Logout (`POST /auth/logout`)

1. Read session cookie (`request.cookies[SESSION_COOKIE_NAME]`), hash it, delete the matching `sessions` row if present.
2. Clear the cookie via `reply.clearCookie`.
3. Always `200 { loggedOut: true }` — logging out twice, or with no cookie at all, is not an error.

### Session check (`GET /auth/session`, used by apps/web's `useSession`)

1. Read cookie → hash → look up `sessions` row → check `expires_at` not passed → join to `customers` for display info (`getCustomerForSessionToken` in `apps/api/src/auth/lib/getSession.ts`).
2. No row or expired → `{ customer: null }`. Does not delete the expired row proactively — lazy cleanup happens whenever the next successful register/login writes a fresh row for that customer; a stray expired row sitting in the table in the meantime is harmless since this lookup already treats it as logged out.

## Open questions / TBD (resolve while implementing, update this doc after)

- ~~Exact API route paths~~ — resolved: `/auth/*` on a standalone Fastify service (`apps/api`), not Next.js route handlers in apps/web. Changed mid-phase — see ADR 0004.
- ~~Password minimum requirements~~ — resolved: length only, 8 characters minimum. No complexity rules (matches NIST 800-63B guidance that length is the stronger signal; complexity rules mostly push users toward predictable substitutions).
- ~~Session duration + sliding vs. fixed~~ — resolved: 30 days, fixed. Simpler to reason about than sliding expiry; revisit if "stay logged in indefinitely while active" becomes a real user complaint.
- ~~Auto-login on register~~ — resolved: yes, register creates a session and sets the cookie immediately.
- ~~Framework for apps/api~~ — resolved: Fastify (`@fastify/cors`, `@fastify/cookie`), over Express/raw `http`. See ADR 0004.
- ~~Cross-origin cookie strategy~~ — resolved: keep the httpOnly cookie (per ADR 0003), solve cross-origin with CORS (specific origin + `credentials: true`) + `credentials: "include"` on the client, rather than switching to a bearer token. `SameSite=Lax` works for local dev because it only cares about scheme + registrable domain, not port.
- **Production `SameSite`/CORS TBD**: if apps/web and apps/api ever deploy to genuinely different registrable domains (not just different ports on `localhost`), this needs revisiting — likely `SameSite=None; Secure`, with the CSRF implications that come with it. Not solved now; flagged in ADR 0004.
- Expired-session cleanup strategy — still TBD (lazy cleanup on next lookup vs. a periodic job). Current behavior (lazy, implicit) is good enough for this project's scale.
- Rate limiting on login attempts (brute-force protection) — still TBD, likely out of scope for this learning project; flagged as a known gap if skipped.
- `sessions.ip_address` is not currently populated — local dev has no reverse proxy setting `x-forwarded-for`, and storing something misleading (e.g. always `::1`) seemed worse than leaving it `null`. Revisit once there's a real deploy target with a known proxy header to trust.
- **Route protection in `apps/web/proxy.ts`** (for `/account`, `/checkout`) — not yet designed. Open question: does the Next.js proxy call out to apps/api on every matched request (adds latency, and apps/api being down would break routing), or is there a cheaper check? Needs its own design pass before building.

## Out of scope for this phase

- Password reset / forgot-password flow.
- Email verification.
- OAuth / social login.
- "Active sessions" management UI (schema supports it later; no UI planned now).

## Testing requirements (per AGENTS.md: security-critical code ships with tests same-change)

All tests below live in `apps/api` and use Fastify's `.inject()` against an in-memory, schema-migrated SQLite DB (not the real `commerce.db`).

- [x] `src/auth/lib/password.ts` — hash/verify round-trip, salting, no-plaintext-leak (`password.test.ts`, 4 tests).
- [x] Session token generation — collision resistance / correct hashing (not the raw value stored) (`src/auth/lib/session.ts`, `session.test.ts`, 4 tests).
- [x] `getCustomerForSessionToken` — no token, unknown token, valid session, expired session (`src/auth/lib/getSession.test.ts`, 4 tests). This is what satisfies "expired session is treated as logged out," below.
- [x] Register endpoint — happy path, duplicate email rejected (case-insensitively), weak password rejected, invalid email rejected, malformed JSON rejected (`src/auth/routes/register.test.ts`, 5 tests). Also manually verified end-to-end against the real dev server + `commerce.db`, with an `Origin` header simulating the browser (cookie attributes, CORS headers, bcrypt hash stored not plaintext, session row hash not raw token, cascade delete).
- [x] Login endpoint — correct credentials succeed, wrong password/email both get the same generic error (`src/auth/routes/login.test.ts`, 7 tests). Manually verified end-to-end: both failure paths return byte-identical 401 bodies, each login creates its own distinct session row.
- [x] Logout — session row actually deleted, cookie actually cleared (`src/auth/routes/logout.test.ts`, 4 tests: deletes matching row + clears cookie, doesn't touch another customer's session, succeeds with no cookie, succeeds when the cookie's session is already gone from the DB). Manually verified end-to-end.
- [x] Session check endpoint — no cookie, valid cookie, expired cookie (`src/auth/routes/session.test.ts`, 3 tests).
- [x] Expired session is treated as logged out — covered by both `getSession.test.ts` and `session.test.ts` above.
- [x] Full three-app integration — `npm run dev` (root) boots cms + api + web together; ran the complete register → session → logout → login → session cycle via curl against the live `apps/api` with proper `Origin` headers, confirming CORS + cookie behavior at every step and that the storefront itself still renders.
